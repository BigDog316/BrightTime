## The schema

The DDL in `db/schema/` is the source of truth (Q12): SQL first, with EF Core mapped to it, and
`SchemaDriftTests` failing on any difference in either direction. There are no EF migrations.
`db/apply-schema.sh` applies the files in order, in one database.

| File | Schema | Holds |
|---|---|---|
| `00-extensions-roles.sql` | | Extensions (PostGIS, citext, pg_trgm, unaccent and others) and the cluster roles |
| `10-platform.sql` | `platform` | Tenants, domains, locales, flags, wording overrides, geography, taxonomy, media, audit, outbox, jobs, retention, subject requests, API clients, key tables |
| `20-identity.sql` | `identity` | Accounts, credentials, refresh tokens, roles, guardian links, consent, youth capabilities, access grants, terms |
| `30-directory.sql` | `directory` | Organisations, sites, hours, memberships, invitations, clearances, vetting |
| `40-opportunity.sql` | `opportunity` | Listings, translations, sessions, occurrences, revisions, the search projection, collections, saved items, reminders |
| `50-enrollment.sql` | `enrollment` | Family profile, shares, forms, eligibility, applications, waivers, seats, enrolments, fees and payments |
| `55-attendance.sql` | `attendance` | Records, sync batches, check-in tokens, devices |
| `60-learning.sql` | `learning` | Learner profiles, participation, issuers and keys, badges, playlists, projects |
| `70-community.sql` | `community` | Conversations, messages, broadcasts, spaces, posts, moderation |
| `80-workforce.sql`, `90-landscape.sql`, `95-analytics.sql` | | Later milestones |
| `96-notify.sql` | `notify` | Push devices, preferences, notifications, deliveries |
| `97-integration.sql` | `integration` | Imports and external systems |
| `99-rls-and-grants.sql` | | **The whole isolation surface**: every policy and grant, and the security-definer functions |

187 tables in all. Conventions ([plan/02](../plan/02-data-model.md)):
- UUIDv7 keys, generated by the application.
- `tenant_id` on every tenant-owned table.
- `timestamptz` throughout, always UTC.
- `citext` for case-insensitive names and slugs.
- Checks and partial unique indexes for the invariants.
- The collation is `C.UTF-8`, because citext comparison and index order depend on it.

## Database roles

| Role | Used by | Row-level security |
|---|---|---|
| `brighttime_owner` | Owns every object | Bound by `FORCE ROW LEVEL SECURITY` |
| `brighttime_migrator` | Applying DDL; owns the security-definer functions | `BYPASSRLS`. The only principal that crosses tenants |
| `brighttime_app` | Web and Api requests | Tenant policy plus the actor guard |
| `brighttime_auth` | The sign-in path only | Tenant policy, exempt from the actor guard, granted on the Identity stores and nothing else |
| `brighttime_jobs` | The worker | Tenant policy, no actor guard. Permissive policies let it claim across tenants on `platform.job` and `platform.outbox_message` only |
| `brighttime_readonly` | Civic and research reads | Suppressed views only |
| `brighttime_finder` | The public finder, entered with `SET LOCAL ROLE` (D13) | `BYPASSRLS`, with `SELECT` on `opportunity.listing_search` and nothing else; a migration check fails if it ever gains more |

Hosts log in as `bt_*_login` roles that are members of these (`deploy/postgres/init-brighttime.sh`
creates them for compose).

## Row-level security

Three layers, all in `99-rls-and-grants.sql`:

1. **Tenant isolation**, permissive, on every table with a `tenant_id`:
   `tenant_id = platform.current_tenant_id()`.
2. **Through the parent**, permissive, on child tables without a `tenant_id`, such as
   `issuer_key` through `issuer_profile`: an `EXISTS` against the already-protected parent.
3. **The actor guard**, *restrictive*, on youth-record tables: `platform.has_actor()`. A request
   with no signed-in person can't read or write a row in them, whatever reaches the query builder.
   Restrictive matters: a second permissive policy would be OR-ed and weaken isolation.

The tenant and actor are transaction-local settings (`set_config(..., true)`), set at the start of
each module transaction, so a pooled connection never carries them forward.

The actor guard covers, among others: `identity.app_user`, guardian links, consents,
capabilities and access grants; `enrollment.family_profile`, `family_member`, `family_contact`,
`profile_share`, `application`, `enrollment`, `waiver_signature`, `payment_intent`; all of
`attendance`'s records, batches and tokens; `learning.participation_record`; community
conversations and messages; and notifications and push devices. The full list is in the file.

**Security-definer functions.** Where an anonymous request must see a narrow slice of a guarded
table, a function owned by `brighttime_migrator` returns exactly that slice, checking the tenant
and the conditions itself:
- `platform.queue_health()`: counts and ages for the readiness probe, never a row.
- `learning.public_participation(tenant, slug)`: the unhidden records of a portfolio its owner
  chose to show (D65).
- The audit partition functions, executable by the jobs role only.

`learning.badge_assertion` sits outside the actor guard on purpose, so public verification can
read it in the tenant without an actor. The public routes return only what the credential itself
carries (D66).

## Rules the database enforces

These are constraints and triggers, not application code, so no bug above the database can break
them:

- **No adult alone with a minor in a conversation** (T1). `enforce_safe_conversation()` refuses at
  commit every route to such a pair. `set_participant_minor()` decides who is a minor from the
  account, never from the caller (D53).
- **Append-only evidence.**
  - `audit_event` partitions are sealed as they are created.
  - `opportunity.listing_revision` refuses updates.
  - `enrollment.waiver_signature` is append-only, and its references restrict deletes.
  - Attendance corrections supersede the old record rather than replace it.
- **The last seat goes to exactly one applicant.** Seats are taken under a `FOR UPDATE` lock on the
  seat pool (D48).
- **No youth home address or coordinates** anywhere in the schema.
- **Clearances are status and expiry only**, never a background-check report.
- **No cardholder data.** Payment rows hold the gateway's ids and statuses.
- **Badges.** A badge is awarded once per recipient while unrevoked. A revocation always has a
  reason. A credential has a proof. Issuer keys are `Ed25519`, `ES256` or `RS256`, with at most
  one active key per issuer.

## Encryption and keys

**Field encryption.** Sensitive fields are AES-GCM encrypted by the application before they reach
the database (`AesGcmFieldCipher`):
- family members' names and dates of birth;
- support-need detail;
- family contacts' names, phones and emails;
- sensitive application answers (sealed);
- account phone numbers;
- push device tokens.

Lookups on an encrypted value use a keyed **blind index** (for example
`identity.app_user.phone_blind_index`, keyed by `platform.blind_index_key`).

**Tenant data keys** are derived per tenant with HKDF-SHA256 from a master key in the vault
(`DerivedTenantDataKeyProvider`): the tenant id is the salt and the version is in the info.
`Security:DataKeys` lists the master key versions held, each with a vault reference. The highest
version encrypts, and every listed version still decrypts.

**The vault.** `IKeyVault` resolves a reference to key material, so only references are ever stored
(`issuer_key.private_key_ref`, `blind_index_key.key_ref`). `ConfiguredKeyVault` reads it from
configuration, for development and single-server installs. A managed vault (Azure Key Vault, AWS
KMS) can replace it behind the same interface.

| Kind | Configuration | Used for |
|---|---|---|
| Symmetric, base64, 32 bytes or more | `Security:Keys:<ref>` | Tenant data master keys, the data-protection key ring (`data-protection`), blind indexes |
| RSA private key, PEM, 2048 bits or more | `Security:SigningKeys:<ref>` or `Security:SigningKeys:default` | Open Badges credentials and CLRs, signed RS256 (D66, D68); each organisation's reference is `badge-issuer-{orgId:N}`, the site's `clr-issuer-{tenantId:N}` |

In Development a missing key is made up for the life of the process. Anywhere else a missing key
stops the operation. See [operations.md](operations.md#keys) for rotation.

**The data-protection key ring** (cookies, antiforgery, one-time tokens) is shared by Web and Api.
It lives in `platform.data_protection_key`, encrypted under `Security:Keys:data-protection`.

**Badge signing.** Each organisation issues under its own `did:web` DID. Its public key is published
in the DID document, and its key id is the RFC 7638 thumbprint. When the vault's key changes, the
old key is retired, not deleted, so older credentials still verify.

## Signing in

| | Web | Api (the app) |
|---|---|---|
| Session | Cookie | 10-minute JWT (HMAC-SHA256) plus a rotating refresh token |
| Password | Argon2id hashes; optional breached-password check (`Auth:CheckBreachedPasswords`, k-anonymity) | Same store |
| Passkeys | WebAuthn | The same store and relying party (`Passkeys:AppOrigins` lists the app's origins) |
| External | OIDC providers under `Auth:External` | The web flow in the system browser, then a one-time PKCE-bound code (`POST /auth/external/token`) |
| Development | `/dev/sign-in`, only in Development with `Auth:DevelopmentSignIn=true` (D14) | |

- **Refresh tokens** rotate on every use and are chained in families (D28). Presenting a spent
  token revokes the whole family and is audited. An adult's session ends after 30 days idle, a
  young person's after 30 minutes (T14). No session outlives 90 days.
- **Access tokens** are signed with the first key in `Auth:Tokens:SigningKeys`, and every listed key
  verifies. To rotate, add a new key first, then remove the old one after the access lifetime.
- **Account changes.** A change to an account (a password, a passkey, "sign out everywhere")
  changes its security stamp, which every request checks. Old tokens and cookies stop working at
  their next request.
- **Step-up.** Changing how an account signs in needs a sign-in within the last
  `Auth:StepUpMinutes` (10 by default).
- **Rate limits.** Sign-in, forgot-password and reset are limited per client address
  (`Auth:SignInAttemptsPerMinute`, 10 by default). The forgot-password answer is the same whether or
  not the address exists.
- **Registration** asks for a birth month only. Under 13 is refused; 13 to 17 makes a youth
  account. A child under 13 exists only as a profile on a guardian's account until a guardian
  consents (email plus, or an organiser-attested signed form, D31) and, at 13, hands it over (D35).

## Permissions

Three separate questions, all of which must be yes ([plan/04](../plan/04-roles-and-permissions.md)):

1. **Tenant.** Is the request in the tenant that owns the data? RLS answers this, and the
   application checks it too.
2. **Role.** Does one of the person's roles grant the permission? Roles are tenant-scoped rows,
   and the permission vocabulary is in code (`Permissions`, with defaults in `BrightTimeRoles`).
   `platform_admin` holds no youth-record permission at all.
3. **Scope.** Does this person's scope cover this object?
   - **Organisation scope** (`OrganisationScopeRequirement(permission, minimumRole)`): a live
     membership in the organisation with at least that role. The order is owner > admin > staff >
     mentor > viewer.
   - **A family's share**: an organisation sees a family's members and fields only through a live
     `profile_share` naming them (D44, D48).
   - **Guardianship**: a verified, unrevoked guardian link.
   - **Capabilities**: a youth account's `youth_capability` (enrol, be messaged, post, upload,
     showcase), recomputed on birthdays, consent changes and terms changes.

Refusals carry a reason code (`badges.forbidden`, `family.link_forbidden`, …) rather than an empty
result: an honest caller should be told why.

## Audit

- **One row per operation** in `platform.audit_event` (D11, D19): who, acting for which
  organisation, what action, the outcome (allow, deny, error), the subject kind and ids, a reason
  where required, and detail.
- It is partitioned by month. The worker creates partitions months ahead
  (`AuditPartitionMaintenance`), and each is sealed as it is created
  (`platform.seal_audit_partition`), so nothing can update or delete a row.
- Client addresses and user agents are kept only as keyed hashes (`Audit:ClientHashKey`, required
  outside Development).
- **Youth-record access** is declared, not remembered:
  - an endpoint or page that touches youth records carries `[YouthRecord(action)]`;
  - a DTO carrying youth data carries `[YouthData]`;
  - a guard at start-up refuses to run a host with an endpoint that can return youth data
    without the attribute;
  - the module writes the access with `AuditTrail.RecordInTransactionAsync` in the same
    transaction as the read, so there is no read without its record.
- Refusals are audited too (`Outcome = Deny`).
- The organiser console's **Audit log** reads it, filtered by action prefix, person, subject,
  outcome and date.

## Youth safety and privacy, end to end

| Concern | Control | Where |
|---|---|---|
| Grooming through messaging (T1) | No adult alone with a minor; an admin observes or it's refused; contact-exchange attempts to a minor held; pushes say only who wrote | Database trigger, Community module |
| Where children are (T4, T6) | No youth addresses; private sites show only a neighbourhood; the finder reads a projection without people in it; check-in codes name nobody | Schema, finder role, Attendance |
| Over-reach by providers (T8) | Names and fields only through a live family share; every read audited | Enrollment, audit |
| Unsafe adult gains access (T9) | Verified guardian links, revocable; consent per scope with the exact text hashed | Identity |
| Insider abuse (T10) | Platform admin has no youth permissions; audit is append-only and sealed | Roles, audit |
| Offline devices (T12) | Sealed marks, a keychain key, a 72-hour lock, remote wipe | App, Attendance |
| Shared devices (T14) | 30-minute youth sessions; refresh reuse revokes the family | Identity, Api |
| Small-cell re-identification (T17) | Reports hide counts under the tenant's threshold, with complementary suppression, and say what they hid | Reporting |
| Payment scope (T20) | Card entry on Stripe's element; webhooks believed only by signature | Enrollment |
| Account takeover (T21) | Passkeys first, Argon2id, breached-password check, step-up, rate limits | Identity, Web, Api |
| Portfolio and badges (T5) | Private by default; display names without the family name; recipients only as salted hashes | Learning |

## Known gaps

- **Cross-schema foreign keys.** [plan/01](../plan/01-architecture.md#database-boundaries) allows
  cross-schema foreign keys only to nine reference tables. The DDL also has 34 others, each
  pointing down the module order (for example `attendance.attendance_record` →
  `enrollment.enrollment`). The planned test that would hold the allowlist doesn't exist yet.
- **Re-encryption on data key rotation** is described in the key provider's design but not built:
  adding a version keeps old data readable, and nothing rewrites it yet.
- **Deletion versus audit** (Q5) and **retention periods** (Q4) are open. Nothing deletes subject
  data yet.
- **Deleting organisations, listings or community reports** would fail against append-only tables
  (D46). That needs a decision before anything deletes them.
